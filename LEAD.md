## 2. Кейс: что требуют (выжимка из брифа Axenix)

**Суть.** Веб-инструмент, который понимает программу и как код, и как граф. Он помогает улучшить программу
и доказывает, что результат после изменений не поменялся. На вход — Java-монолит примерно на 1000 строк в одном файле.

**Пользовательский путь:** загрузить `.java` → разобрать → построить граф → исследовать и править → собрать Java → запустить
и сравнить. **Изменения синхронизируются в обе стороны.**

**Ключевой контракт кейса:** после любых преобразований автоматические тесты подтверждают, что поведение сохранилось.

**Диагностика.** Для каждой проблемы пользователь видит строку кода и узел графа, объяснение, оценку сложности метода
или фрагмента и вариант исправления с ожидаемым эффектом. Требование организаторов: *«Диагноз должен быть
проверяемым, а не только красивым».*

**Оптимизация и декомпозиция.** При необходимости монолит автоматически разбивается по ответственностям, например
`Parser / Analyzer / Optimizer / Main`. Quality gate: сборка + автотесты = поведение сохранено.

**Обязательная поддержка Java (разделы 1–4):**
1. **Язык и java.lang:** классы и интерфейсы, примитивы, обёртки, массивы, арифметика, логика, сравнение, приведение;
   if/else, switch, циклы, break/continue/return; методы, конструкторы, поля, static; try/catch/finally, throw;
   Object, String, Math, System.
2. **Консольный ввод-вывод:** System.in/out/err, Scanner, Formatter, String.format, printf, StandardCharsets (кириллица).
3. **Коллекции java.util:** Collection, Iterable, List/Set/Map, ArrayList, LinkedList, HashSet, TreeSet, HashMap,
   TreeMap, Iterator, Collections, Arrays, Comparator, Optional, List.of / Set.of / Map.of.
4. **Исключения:** проверяемые и непроверяемые, throws и обязательный catch, свои исключения через наследование.

**Бонус:** record, enum, дженерики, лямбды и java.util.function, Stream API и Collectors.

**Не оценивается:** многопоточность, рефлексия, работа с файлами (java.nio.file), сеть, java.time.

**Правила.** ИИ и любые библиотеки разрешены. Тестовые монолиты организаторы делают сами с помощью ИИ и проверяют вручную.
**Их нужно запросить у менторов и добавить в `corpus/`.**

**Демо:** монолит → граф → диагноз → улучшение → тесты. Полный путь показываем на одном примере.

**Предварительные критерии оценки** (веса организаторы объявят отдельно):
- поддержка обязательного scope Java;
- сохранение поведения;
- польза диагностики и оптимизации;
- понятность интерфейса;
- качество реализации и демо.

**Что сдаём:**
1. исходный код с инструкцией запуска;
2. веб-демо — ссылку или воспроизводимую сборку;
3. автотесты и результат их запуска;
4. описание решения: архитектура, поддержанный scope, ограничения.

## 3. Принятые решения и почему

| # | Решение | Почему | Что потеряем, если изменим |
|---|---|---|---|
| D1 | **AST — источник истины, граф — только проекция** | Синхронизация в обе стороны работает сама: правка графа = операция над AST → печать кода → новый граф. Расхождений нет по построению | Если хранить граф отдельно, придётся писать двустороннюю синхронизацию двух моделей, а это главный источник багов |
| D2 | **JavaParser + LexicalPreservingPrinter** | Единственный зрелый Java-парсер, который сохраняет форматирование нетронутого кода. Round-trip уже проверен тестом | Генерация через pretty-print переформатирует весь файл, и дифф для жюри станет нечитаемым |
| D3 | **Поведение проверяется дифф-тестами:** версия 1 и текущая запускаются на одних входах | Не нужно писать тесты вручную под каждый монолит; прямо отвечает ключевому контракту кейса | — |
| D4 | **Код пользователя запускается в отдельном контейнере `runner`** без сети и с лимитами | Мы исполняем чужой код; изоляцию ещё и можно показать жюри как плюс | — |
| D5 | **Два уровня графа:** обзор (классы и вызовы) и блок-схема метода | 1000 строк в одной блок-схеме нечитаемы | — |
| D6 | **Оптимизации:** сначала детерминированные правила, LLM — только как дополнение и только после quality gate | Предсказуемо на демо, и диагноз можно проверить | — |
| D7 | **Стек:** Java 21 + Spring Boot 3.4 + Maven; React + TS + Vite + React Flow + elkjs + Monaco | JavaParser живёт в JVM; React Flow ближе всего к макету из брифа | — |
| D8 | **Состояние проектов — в памяти** (версии, версия 1 = эталон) | Для демо персистентность не нужна | После рестарта api проекты пропадают, и это нормально |
| D9 | **Неподдерживаемая конструкция → узел `raw`, а не падение** | Разбор любого монолита не ломается | — |
| D10 | **Notion — слой координации поверх git** | Удобнее для живой доски и вопросов между ролями. Код, контракты и документация — только в git | — |

Новые решения вносим сюда и коротко дублируем в Notion → «Решения».

## 5. Как менять план (полномочия роли 0)

Роль 0 владеет файлами `LEAD.md`, `PLAN.md`, `CLAUDE.md`, структурой и приоритетами в `STATUS.md` и Notion-штабом.
Роль 0 **арбитр контрактов**: если владельцы контрактов (роль 1 — граф, роль 4 — API) не договорились, решает лид.

**Процедура изменения плана:**
1. Записать причину и новое решение в §3 этого файла (новая строка D-N) и в Notion → «Решения».
2. Поправить `PLAN.md`, `STATUS.md` и при необходимости `CLAUDE.md` одним PR с префиксом `plan:`.
3. Обновить карточки на Notion-доске: приоритеты, перенос, «Заблокировано».
4. Если задело контракт — создать запись «Изменение контракта» в «Вопросы и запросы», адресовать владельцу,
   дождаться его PR. Самому контракт не править, разве что владелец недоступен больше 2 часов.
5. Сообщить команде в Telegram одной строкой: что поменялось и чьи задачи это задевает.

**Когда пересматривать план:**
- **После интеграции №1 (H10)**, если полный путь на одном примере не проходит → режем scope по лестнице ниже.
