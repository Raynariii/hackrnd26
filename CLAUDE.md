# CLAUDE.md — правила для агентов команды

Проект: **Java Blueprints** (хакатон, кейс Axenix). Веб-инструмент: Java-монолит → граф → диагностика → улучшение →
автоматическая проверка, что поведение сохранилось. Полный план — `PLAN.md`, текущее состояние — `STATUS.md`.

## В начале каждой сессии
1. `git pull --rebase origin main`
2. Прочитать `PLAN.md` (свою роль), `STATUS.md` (что готово, что блокирует), нужные файлы в `contracts/` и
   `LEAD.md` §3–4 (принятые решения и известные риски — не переизобретай то, что уже решено).
3. Notion (если подключён): открытые записи в «Вопросы и запросы», где «Кому» = твоя роль или «все»; карточки своей
   роли на доске «Задачи». Взял задачу → карточка в «В работе», в поле «Ветка» — имя ветки.
4. Работать в ветке `feat/<роль>-<что>` (например `feat/core-method-flow`). Подроль роли 2 — `feat/analysis-<2a|2b|2c|2d>-<что>`.
5. Несколько агентов на одной машине — у каждого свой `git worktree` (см. `PLAN.md` §6.1), никогда не один каталог на двоих.

## В конце каждой сессии / задачи
1. Тесты своего модуля зелёные (команды ниже).
2. Обновить свою секцию в `STATUS.md`: что сделано, что дальше, блокеры.
3. Коммит + PR в `main`. PR маленькие — раз в 1–2 часа работы. Сливаем только при зелёном CI.
4. Notion (если подключён): карточка задачи → «Ревью» со ссылкой на PR (после слияния → «Готово»);
   одна запись в «Журнал агентов» — роль, сделано, дальше, блокеры, ссылка на PR.

Правила:
- Значения полей «Роль» / «От роли» / «Кому»: `0 — лид`, `1 — ядро`, `2 — анализ`, `3 — фронт`, `4 — песочница/API`, `все`.
  Статусы задач: `Бэклог`, `В работе`, `Ревью`, `Заблокировано`, `Готово`.
- **Список задач ведётся в `STATUS.md`.** Новая задача → сначала пункт в `STATUS.md` (в PR), затем карточка в Notion.
  Закрыл задачу → галочка в `STATUS.md` **и** карточка в «Готово». Расхождение = правда в `STATUS.md`.
- **Запросы на изменения** (контракт, чужая зона) создаются в «Вопросы и запросы» вместо правки чужих файлов.
  Владелец отвечает там же; принятое изменение попадает в репозиторий только PR-ом владельца, ссылка на PR — в запись.
- Долгие обсуждения и черновики — в Notion; итог, влияющий на код, — в `docs/` или `PLAN.md` через PR.
- Никаких секретов (ключи, токены, `.env`) в Notion.
- Notion недоступен или не подключён — работай только через git, это не блокер.

в Notion «Вопросы и запросы» (без Notion — строку в «Запросы на изменения» в `STATUS.md`) и сообщи человеку.

## Контракты — источник правды
- `contracts/graph.schema.json` — формат графа. Java: `io.blueprints.core.graph.*`. TS: `frontend/src/api/types.ts`.
- `contracts/openapi.yaml` — REST API. Java DTO: `backend/api/.../web/Dto.java` и контроллеры. TS: `frontend/src/api/types.ts`.
- Код следует за контрактом, не наоборот. Поменял контракт (только владелец!) — поправь Java-модели и `types.ts` в том же PR.

## Архитектурные правила
- **AST — источник истины.** Граф только проекция. Любая правка графа = операция над AST → печать кода → новый граф.
- Форматирование кода сохраняется: парсинг через `JavaProjectParser` (LexicalPreservingPrinter), печать через `CodeGenerator`.
- `core` и `analysis` — чистые библиотеки: без Spring, без HTTP, без состояния. Spring — только в `api` и `runner`.
- Пользовательский код компилируется и запускается **только** в `runner` (контейнер без сети). Никогда — в процессе `api`.
- Новое правило анализа = класс, реализующий `io.blueprints.analysis.Rule`, + строка в реестре правил + тест
  (реестр — `Analyzer.defaultRules()`, после задачи 2a-P0 — `rules/Rules.java`). Правила добавляет только 2a.
- Публичный API модуля `analysis` для роли 4 заморожен: `Analyzer.withDefaultRules().analyze(model)`, record `Finding`
  (= контракт), `FixEngine#apply(files, findingId)`, `Decomposer#propose(model)`. Внутри подроли рефакторят свободно,
  сигнатуры меняют только с запросом роли 4.
- Неподдерживаемая конструкция Java не должна ронять разбор: в графе она становится узлом `raw` с исходным кодом.
- Id узла графа, построенного из AST, — `"g" + astId` (start/end блок-схемы — `<id метода>:start` / `:end`).
  На этом соглашении держатся ссылки `Finding.nodeIds` → узлы. Не меняй его без решения лида.
- Любая оптимизация (правило или LLM) применяется только после зелёного quality gate: компиляция + дифф-тесты.

## Команды
```bash
# бэкенд: сборка и все тесты (Java 21+, Maven)
cd backend && mvn -B verify
# только один модуль (с зависимостями)
cd backend && mvn -B -pl core -am verify

# api локально (нужен runner для /run)
cd backend && mvn -B -pl runner -am spring-boot:run   # :8090
cd backend && mvn -B -pl api -am spring-boot:run      # :8080

# фронт
cd frontend && npm ci
npm run dev        # :5173, проксирует /api на :8080
npm run dev:mock   # без бэкенда, на фикстурах из src/mocks
npm run build      # typecheck + сборка

# всё вместе как у жюри
docker compose up --build   # http://localhost:3000
```

## Стиль
- Java 21: records для DTO и моделей, без Lombok. Пакеты `io.blueprints.<модуль>`.
- Тексты для пользователя (сообщения, объяснения находок, UI) — на русском. Код, идентификаторы — на английском.
- Тесты: JUnit 5 + AssertJ (бэкенд). Каждая новая функция ядра/анализа — с тестом.
- Не добавляй зависимости без необходимости; новая зависимость — упомяни в PR.

## Нельзя
- Пушить напрямую в `main`, переписывать чужую историю, коммитить `.env` и ключи.
- Менять контракты, не будучи их владельцем.
- Оставлять `main` в несобираемом состоянии.
